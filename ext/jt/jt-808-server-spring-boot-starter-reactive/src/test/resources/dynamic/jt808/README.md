# JT/T 808 动态 DSL 样例

这里的 JSON 是完整、可独立导入的 `DynamicSchema` 定义。每份定义按线上顺序描述消息头、消息体和末尾的校验字节；测试入口是 `Jt808DynamicDslTest`。

| 文件                      | 对应报文                            | 主要展示的能力                                        |
|---------------------------|-------------------------------------|-------------------------------------------------------|
| `8003-2013.json`          | 2013 版服务器补传分包请求           | 6 字节 BCD 终端号、8 bit 数量和按数量读取的数组       |
| `8003-2019.json`          | 2019 版服务器补传分包请求           | 10 字节 BCD 终端号、协议版本号、16 bit 数量和数组     |
| `8003-multi-version.json` | 2011/2013/2019 版服务器补传分包请求 | 方案二：独立位字段、自动回填消息体长度、自动生成数量和 XOR 校验码 |
| `8003-multi-version-derived.json` | 2011/2013/2019 版服务器补传分包请求 | 方案一：派生位段反向合成原始属性值、自动生成数量和 XOR 校验码 |
| `0200-2019.json`          | 2019 版位置信息汇报                 | 固定定位字段、BCD 时间和保留顺序的 TLV 附加项         |
| `0704-2019.json`          | 2019 版定位数据批量上传             | 消息体长度引用、记录数量引用、每条记录的 u16 长度前缀 |

把 JSON 文件导入通用调试页的“自由组合”模式后，可以使用下列原始 HEX 解码。这里的输入均已去掉两侧 `7e`，且样例中没有需要反转义的字节；编码输出也不添加帧标识或转义。

```text
8003-2013: 800300090139123443230000006f030002000300049d
8003-2019: 8003400a01000000000139123443290000006f0003000200030004d5
0200-2019: 02004026010000000001391234432900000000006f0000001601dc9a0707456246007b004200032501292233440202006401040000000c41
0704-2019: 0704403f01000000000139123443290000000200001c000000010000000101d907f2073d336c029a00210059241029213903001c000000010000000101d907f3073d336d03090043005a241029213903f8
```

四份单版本样例和方案一通过 `derived` 将 `bodyProps` 的低 10 位显示为 `bodyLength`；方案二直接读取低 10 位的 `u10` 字段。消息体 `struct` 均以该长度为边界。`0x0200` 的附加信息用 8 bit 标签和 8 bit 长度表示；定义中列出的标签 1、2 会解成数值，其他标签由 `tlv` 保留为 `rawHex`。BCD 时间保留 `yyMMddHHmmss` 数字串。

两份多版本样例均可导入调试页后选择目标协议版本 2013 或 2019，并输入上表对应 HEX。Java 调用方使用 `DynamicCompiler.compile(schema, 2013)` 或 `compile(schema, 2019)`，分别持有并复用计划。2011 与 2013 使用相同布局，可用 2013 的 HEX 和字段值验证。版本由调用方指定，定义不自动识别报文版本。

## 方案二：独立位字段和自动长度回填

`8003-multi-version.json` 将原来的 `bodyProps: u16` 按默认的大端、`msb0` 顺序拆成以下位字段，筛选目标版本后总宽度仍为 16 bit：

| 字段 | 原始属性位 | 编码值来源 |
| --- | --- | --- |
| `reserved` | 15 | 固定为 0 |
| `versionFlag` | 14 | 编译版本为 2011/2013 时固定为 0，2019 时固定为 1 |
| `hasSubpackage` | 13 | 调用方提供 0 或 1 |
| `encryption` | 12～10 | 调用方提供加密方式的数值 |
| `bodyLength` | 9～0 | `u10` 通过 `computedLengthOf: "body"` 回填实际消息体字节数 |

`subpackage` 的条件改为 `hasSubpackage == 1`。写入消息体前，长度位段暂时留空；写完后只回填这 10 位，保留同一字节中的其他属性位，随后计算校验和。回填值超出 10 位范围时编码失败。解码结果返回各个独立位字段，不再包含原始 `bodyProps` 数值。

两份多版本样例的 `body.packageCount` 都通过 `generated.countOf: "packageIdList"` 生成，2011/2013 使用 `u8`，2019 使用 `u16`。调用方无需填写数组数量。

选择 2013 版后，在调试页输入以下字段值即可生成上面的 `8003-2013` HEX，消息体长度为 9 字节、包数量为 3，校验码为 `9d`：

```json
{
  "messageId": 32771,
  "hasSubpackage": 0,
  "encryption": 0,
  "terminalId": "013912344323",
  "serialNo": 0,
  "body": {
    "originalMessageFlowId": 111,
    "packageIdList": [2, 3, 4]
  }
}
```

选择 2019 版时，将 `terminalId` 改为 `"00000000013912344329"`，并添加 `"protocolVersion": 1`，其余业务字段保持相同即可生成上面的 `8003-2019` HEX。`versionFlag` 自动为 1，消息体长度因数量字段变为 `u16` 而自动变为 10 字节，校验码为 `d5`。

## 方案一：派生位段反向合成

`8003-multi-version-derived.json` 保留 `bodyProps: u16`，再用不占报文字节的 `derived` 字段读取长度、加密方式、分包标识、版本标识和保留位。编码输入省略 `bodyProps` 时，编码器用同级输入中的这些位段合成源整数，无需调用方移位或按位或。

选择 2019 版后，以下输入会合成 `bodyProps = 0x400a`，并生成上面的 `8003-2019` HEX：

```json
{
  "messageId": 32771,
  "bodyLength": 10,
  "encryption": 0,
  "hasSubpackage": 0,
  "versionFlag": 1,
  "protocolVersion": 1,
  "terminalId": "00000000013912344329",
  "serialNo": 0,
  "body": {
    "originalMessageFlowId": 111,
    "packageIdList": [2, 3, 4]
  }
}
```

选择 2011/2013 版时，填写 `bodyLength = 9`、`versionFlag = 0`、`terminalId = "013912344323"`，并省略 `protocolVersion`，即可合成 `bodyProps = 0x0009`。未提供的保留位在合成时补零。也可以直接提供原始 `bodyProps`；同时提供的派生位段必须与它一致，重叠位段也必须彼此一致。

方案一解码返回原始 `bodyProps` 和派生位段。它免掉位拼接，但消息体长度和版本标识仍由调用方提供；方案二则自动生成这两项。两种方案都自动生成包数量和校验码。

## 校验和

两份多版本样例的末尾校验字段配置如下，同一份 Schema 和同一个编译计划即可同时用于编码与解码：

```json
{
  "id": "checksum",
  "name": "校验码",
  "type": "u8",
  "generated": {
    "checksum": {
      "algorithm": "xor8",
      "range": "messageId..body"
    }
  }
}
```

`messageId..body` 表示从 `messageId` 的起始字节到 `body` 的末尾字节，包含两端字段和中间字段实际占用的字节。因此校验覆盖当前协议版本的消息头、存在时的分包信息以及整个消息体，不包含末尾的 `checksum`。方案二的长度回填先完成，再计算覆盖整个消息头和消息体的校验和；方案一的派生字段不重复占用报文字节。

编码时可以省略 `checksum`，计划对范围内最终编码的字节逐个异或，再写出一个 `u8` 校验字节。

解码时 `checksum` 仍然从报文中读取一个字节，解码结果保留实际读取到的值，同时根据同一范围重新计算并核对。上述 2013 版报文返回 `checksum = 157`（`0x9d`），2019 版报文返回 `checksum = 213`（`0xd5`）。

默认调用 `plan.decode(input)` 时，校验不匹配也返回完整字段值，并正常推进 `readerIndex`。调用方通过 `result.checksums()` 查看核对结果，其中 `actual()` 是报文值、`expected()` 是计算值、`matched()` 表示是否匹配。调试页也会展示这份结果和跟踪警告，方便分析损坏报文。

严格处理报文时，显式调用 `plan.decode(input, DynamicDecodeOptions.STRICT)`；校验不匹配会抛出字段路径为 `$.checksum` 的 `DynamicCodecException`，输入缓冲区的 `readerIndex` 保持不变。自定义资源限制可使用 `DynamicDecodeOptions.STRICT.withLimits(limits)`，同一 Schema 和编译计划可用于两种模式。数据不足或结构边界错误在两种模式下都会失败。

**当前边界：** 四份单版本样例仍需调用方提供正确的 `bodyProps`、数量字段和普通 `checksum`；两份多版本样例已配置数量与校验和生成，其中方案二还自动回填长度。`hasSubpackage` 和 `encryption` 仍由调用方提供；分包标识为 1 时还需提供 `subpackage.total` 和 `subpackage.index`。上述 JSON 描述的是各自指定版本的消息头和消息体结构；分包重组、加解密和转义由协议层处理。

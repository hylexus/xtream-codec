# Spec Delta

## Purpose

确保 Java 二进制、源码、文档及聚合归档携带清晰、可追溯的项目许可证与源码归属信息，使下游获得分发时所需的声明，并能区分已确认的许可材料与尚待核实的来源。

## ADDED Requirements

### Requirement: Java 归档许可材料

系统 SHALL 在普通、源码和 Javadoc JAR 的 META-INF 中包含与仓库原文一致的 LICENSE.txt、NOTICE.txt、THIRD-PARTY-SOURCE-NOTICES.txt。普通类库 SHALL 不因声明独立依赖而复制其许可清单或完整源码；依赖报告 SHALL 保留显式生成入口。

#### Scenario: 独立获取发布归档

- **WHEN** 用户构建普通、源码或 Javadoc JAR
- **THEN** 每个归档均包含完整的项目许可证与归属声明，依赖报告不覆盖项目 NOTICE

### Requirement: 聚合归档保留第三方声明

系统 SHALL 在 Studio Shadow JAR 中保留来源不同但路径相同的第三方 LICENSE 与 NOTICE 内容，且携带项目许可、NOTICE 和应用共用的补充许可汇总。类库和应用打包 SHALL 不强制生成或携带独立依赖报告，报告 SHALL 保留显式入口。

#### Scenario: 依赖包含同名声明文件

- **WHEN** 用户构建包含多个依赖的 Studio Shadow JAR
- **THEN** 同名 LICENSE 与 NOTICE 的内容被保留，下游可读取项目与第三方归属信息

### Requirement: NOTICE 双语项目说明

项目 SHALL 在根 NOTICE 和 THIRD-PARTY-SOURCE-NOTICES.txt 中对项目自写的适配范围、作者归属、比较版本限制、材料位置及未确认范围提供中文在前、英文紧随的逐句或逐义对照，详细逐文件对应关系 SHALL 使用中英字段标签并保留字段原值。上游版权行、转载 NOTICE 及源码头引用原文 SHALL 完整保留，译文 SHALL 不修改许可证条款或推定已取得未确认的授权。现有分发机制 SHALL 保留 UTF-8 双语内容。

#### Scenario: 阅读和分发双语声明

- **WHEN** 用户查看根 NOTICE、THIRD-PARTY-SOURCE-NOTICES.txt 或获取包含相应源码的 Java 归档
- **THEN** 项目说明具有对应的中英文表达，上游原文保持完整，且归档保留双语文字

### Requirement: 项目免责及无背书说明

项目 SHALL 将中英项目状态、免责、第三方商业承诺和来源展示的详细说明集中在文档声明页。仓库 README 顶部、文档首页首屏及导航 SHALL 提供醒目的说明或入口。完整说明 SHALL 明确项目免费开源、目前无官方商业版、按适用许可证和法律处理担保及责任，第三方自行承担其产品、服务和承诺。如实注明使用 xtream-codec 并附链接属于可选的来源展示；宣传 SHALL 避免通过项目名称、作者身份或标志造成官方关系或背书的误解。许可证要求的归属及已授予的商业使用权 SHALL 保留，现有许可证原文 SHALL 不修改。根 NOTICE 和前端 NOTICE SHALL 保留相同的简短双语项目说明前缀，链接到完整说明，并随 Java 归档及八个前端汇总分发。

#### Scenario: 查看项目或文档首页

- **WHEN** 用户打开仓库 README 或文档首页
- **THEN** 可醒目看到依适用许可证使用、修改、再分发和商用的摘要，并可进入完整中英说明

#### Scenario: 第三方商业化和宣传

- **WHEN** 第三方依适用许可证商用、修改或再分发项目
- **THEN** 完整说明明确其自行承担商业承诺，宣传应准确说明与项目的关系，并保留正常来源署名和既有商用权利

#### Scenario: 如实注明来源并附项目链接

- **WHEN** 用户通过仓库、文档或随包 NOTICE 进入完整声明
- **THEN** 完整说明明确可如实注明使用 xtream-codec 并附项目链接，解释如何避免造成官方关系或背书的误解，并保留分发时适用的归属要求

#### Scenario: 了解修改分发和商业使用权利

- **WHEN** 用户查看 README 或文档首页摘要、完整说明页或随包项目 NOTICE
- **THEN** 中英摘要明确遵守适用许可证即可使用、修改、再分发及商用。完整说明明确无需另行向作者申请商业授权，并保留适用的版权、许可、归属、修改说明及源码提供等要求

#### Scenario: 独立获取 Java 或前端产物

- **WHEN** 用户构建并获取 Java 归档或任一前端产物
- **THEN** 相应 NOTICE 或汇总保留简短中英说明及完整文档入口，上游版权、许可和归属原文保持完整

#### Scenario: 通过 Spring 类比理解权利和责任

- **WHEN** 用户阅读完整声明页中的中英示例
- **THEN** 示例限定为 Apache-2.0 的 Spring Framework 代码，解释许可证本身授予使用权且独立商业支持另行约定，使用依赖不自动产生官方背书或转移自身代码及商业承诺的责任；示例仅帮助理解且不更改适用许可证、法律及另行约定

### Requirement: 来源记录按证据表述

项目 SHALL 仅根据已核实的源码对应关系表述复制或改编；仅有技术参考链接且未建立源码对应关系的文件 SHALL 在仓库记录中中性说明，不推定复制事实或授权缺失。分发声明 SHALL 保留适用归属与许可范围，复制或改编源码的仓库记录 SHALL 保留固定来源、必要证据限制和具体未解决事项，避免重复审查过程及逐文件哈希清单；文字整理 SHALL 不删改上游版权、转载声明和许可原文，也不将待办视为已解决。

#### Scenario: 文件仅有参考链接

- **WHEN** 核对文件注释中的技术参考链接，但未建立具体源码改编对应关系
- **THEN** 仓库记录如实说明链接及比较结果，分发声明不由该链接推定复制或缺少授权，其他已确认的归属和未解决事项继续保留

### Requirement: 已确认派生源码归属保留

系统 SHALL 保留已核实 Spring Framework、Spring Boot、Spring Boot Admin 和 Reactor 派生文件的上游版权与已有修改说明，区分上游版权与项目修改版权。上游比较类的作者归属 SHALL 单独记录，不呈现为当前项目新增作者。许可证格式化任务 SHALL 不覆盖这些上游版权行。来源核实限制 SHALL 在审查记录中明确说明。

#### Scenario: 检查或格式化派生源码

- **WHEN** 用户执行许可证检查或格式化任务
- **THEN** 已恢复的上游版权声明保持完整，未核实来源不被宣称已完成授权核实

### Requirement: MIT 派生源码声明

系统 SHALL 为已核实的 SmallChi JT808/JT1078、EyerH264Decoder、maz-g711 派生源码保留适用的 MIT 版权和许可全文，并明确项目修改部分的许可。系统 SHALL 在相应 Java 普通、源码、Javadoc 归档中携带这些全文；许可证格式化 SHALL 不覆盖这些声明。未包含这些后端源码的独立前端产物 SHALL 不无条件附带这些声明。

#### Scenario: 获取包含 MIT 派生源码的归档

- **WHEN** 用户构建包含已核实 MIT 派生文件的分发归档
- **THEN** 归档包含完整上游 MIT 声明，源码文件区分上游权利与项目修改且保持原有功能

### Requirement: 其他已核实来源声明

系统 SHALL 为已确认的 matrixy、ldming 镜像、sky 解码器和 Micrometer 派生范围保留各自的适用许可与声明，并在许可头检查和分发材料中保持这些内容。经维护者确认、由维护者原创的复用代码 SHALL 从对应贡献授权待办中移除。尚待核实的具体源码复用 SHALL 记录证据缺口，不推定适用其他文件的许可。技术方案参考及项目介绍链接 SHALL 与源码复用分别记录，不应仅凭这些参考关系推定缺少源码授权。

#### Scenario: 继续核实来源

- **WHEN** 维护者确认复用代码由其原创，或取得可对应现用代码的固定上游许可
- **THEN** 审查记录反映该依据，分发保留适用材料，并明确剩余未确认范围

#### Scenario: AAC 注释说明技术方案参考

- **WHEN** AAC 类注释所指为参考 sky 的 7 字节 ADTS 头处理思路，链接用于介绍相关项目，且未建立具体源码复制或改编对应关系
- **THEN** 注释和来源记录说明该参考范围，历史查询证据保留，不因该参考关系本身设立覆盖整个类的源码授权待办，也不将消息解码器的 Mulan 许可扩展到该类

### Requirement: 音频许可及源码材料

系统 SHALL 随 ADPCM 实现提供适用的 MPL-2.0 全文、来源与修改说明、对应 Java 源码，并保留专用许可头检查。包含 jump3r 的分发 SHALL 提供与实际运行时版本一致的源码归档、LGPL 全文、上游声明及可执行的重建和 Boot 嵌套库替换方法。尚未确认的授权范围 SHALL 明确记录。

#### Scenario: 构建 JT1078 应用

- **WHEN** 用户构建实际捆绑 jump3r 的 Boot 或 Shadow 应用
- **THEN** 应用分发包含匹配的源码和许可材料，源码无法解析时应用打包失败，重建工具可编译源码并替换 Boot 中的库；仅声明独立依赖的普通库无需这些材料

### Requirement: jump3r 按分发义务维护

项目 SHALL 依据 jump3r 上游包级许可和发行材料维护未修改的依赖，不维护逐文件许可头分类统计或固定版本哈希门禁。材料检查 SHALL 以自动生成的实际坐标核对对应版本源码和分发文件的校验值，缺失源码、版本不符或文件损坏 SHALL 导致失败。LGPL、上游原文及现有重建/替换支持 SHALL 保留；FFT 的具体历史声明疑问 SHALL 仅保留简短待办，不将日常升级扩展为全库源码审计。

#### Scenario: 升级未修改的 jump3r

- **WHEN** 应用使用另一版本的 jump3r 且分发材料对应实际版本
- **THEN** 检查无需新增固定哈希放行项即可通过，维护者按上游许可和发行材料检查变化，无需逐文件复核

#### Scenario: jump3r 分发材料不对应

- **WHEN** 实际嵌套库与声明版本不一致、对应源码缺失或分发文件与自动生成校验值不一致
- **THEN** 材料检查失败并指出具体缺失或不匹配，不因移除固定版本门禁而跳过这些检查

### Requirement: 源码及 jump3r 材料集中维护

项目 SHALL 将七份复制源码许可与声明的原文合并到 `licenses/source/open_source_licenses.txt`，许可头检查从分节提取适用原文。jump3r 的说明及四份 LAME 原文 SHALL 合并到 `licenses/jump3r/NOTICE.txt`；重建及替换 SHALL 共用 `build-script/license/jump3r.py`，随应用分发时仍与匹配源码同目录。两份审查 JSON SHALL 删除，必要的固定来源、限制和未解决事项 SHALL 保留在现有文档，不重建逐文件哈希清单。LGPL-2.1、MPL-2.0 全文 SHALL 继续保留。

#### Scenario: 集中材料后构建归档

- **WHEN** 用户检查源码许可头并构建 Java 类库或包含 jump3r 的应用
- **THEN** 原文和已有许可头保持完整，归档仅携带相应汇总和适用特殊材料，重建及替换命令仍可执行，旧的分散文件与审查 JSON 不再打包

### Requirement: 前端许可全文

系统 SHALL 为 Studio、两个 Dashboard、四个示例/debug UI 和 docs 的生产构建生成 THIRD-PARTY-FRONTEND-NOTICES.txt，包含实际输出 JavaScript 模块和加载样式所属包的完整许可和归属文本，以及适用的已复制模板许可。缺少许可文本 SHALL 使构建失败。后端资源复制 SHALL 保留该文件。

前端汇总 SHALL 保留项目 Apache LICENSE、根 NOTICE 开头的项目名称/URL/版权归属和适用静态资源材料，SHALL 不无条件加入无关的后端源码声明。npm 许可正文 SHALL 仅在完整文本相同时去重，且保留每个包的名称、版本、许可文件路径及其正文引用；不同版权或条款 SHALL 不因 SPDX 名称相同而合并。

#### Scenario: 构建并嵌入前端

- **WHEN** 用户执行任一前端生产构建并将静态资源复制到后端
- **THEN** 静态分发与后端归档均携带前端许可全文，包版本来自实际安装路径而非范围推定

#### Scenario: 手工分发字体

- **WHEN** docs 构建复制 public 中的 Font Awesome 字体
- **THEN** 字体目录保留原始完整许可和双语来源、版本、归档成员及分发说明，前端汇总包含两份全文，站点完整复制 CSS 引用的字体和材料；不维护固定字体审查哈希或额外清单，显式指定的材料缺失时构建失败

#### Scenario: 多个包使用相同许可正文

- **WHEN** 多个实际收集的包带有完全相同的许可正文，或相同 SPDX 名称但不同版权的正文
- **THEN** 相同正文只输出一次且每个包保留明确引用，不同正文完整分别保留，工具辅助代码、模板与字体声明仍保留

#### Scenario: 阅读前端双语汇总

- **WHEN** 任一前端生产构建生成 THIRD-PARTY-FRONTEND-NOTICES.txt
- **THEN** 共享生成器提供中文在前、英文紧随的标题、自动生成提示、收集范围、许可边界和分发要求，字段标签及项目补充说明具有中英对照，包名、版本、路径、URL 和上游原文保持完整，后端分发保留这些 UTF-8 内容

### Requirement: 前端补充许可的轻量维护

少量 npm 补充许可 SHALL 集中维护于 `licenses/frontend/open_source_licenses.txt`，保留适用包名、比较版本、固定来源及上游原文，完整进入各前端汇总；各节仅适用于实际包含的相应组件。构建 SHALL 按文件中的适用包名及 MIT 声明采用补充，不维护精确版本映射、重复正文或额外审查哈希；包自带的完整原文 SHALL 保留，未知缺失许可 SHALL 使构建失败。普通 npm 依赖 SHALL 不要求逐文件源码审计。

#### Scenario: 补充许可包升级

- **WHEN** 已列包升级且仍声明 MIT，或新版本自行附带完整许可
- **THEN** 升级不因缺少精确版本映射而失败，包自带原文保留；补充原文按上游许可和发行材料维护，未知缺失许可仍报错

### Requirement: 独立绘制的项目标志

项目 SHALL 提供独立绘制的彩色、单色和字标 SVG，以及可重现导出的 PNG、ICO 和站点图标，并替换文档、各前端、Dashboard 内联组件和 IDE 中现用的旧标志。来源记录 SHALL 说明新资源的生成方式及许可范围，不将原截图、示意图推定为新作。

#### Scenario: 构建包含新标志的前端

- **WHEN** 维护者导出标志并构建文档或任一前端
- **THEN** 实际标志引用与产物使用新图形，保留可编辑源文件，旧图片来源仍按具体资源跟踪

#### Scenario: 生成主标志及其派生资源

- **WHEN** 维护者运行 Python 生成器或完整导出命令
- **THEN** Python 从代码中的几何参数生成 `mark.svg`，完整导出以生成的主 SVG 同步各派生资源

### Requirement: 简单静态资源替换

项目 SHALL 以直接编写的 SVG 替换来源未确认的文档首页背景和 debug UI 拖拽图标，保留各自用途，停止在站点中分发旧背景，并记录新资源来源与许可范围。

#### Scenario: 构建文档及调试界面

- **WHEN** 用户构建 docs 和 JT808 debug UI
- **THEN** 产物使用新背景与拖拽图标，原有页面内容和拖拽调用保持可用，未核实的截图仍保留具体待办

### Requirement: 依赖许可检查入口一致

项目 SHALL 让 `checkLicense` 和 `enforceLicenses` 使用同一个依赖报告与白名单，实际检查运行时依赖，支持检查任务所需的 JSON 渲染器，不因空扫描而宣告通过。未获白名单匹配的依赖 SHALL 导致显式检查失败并输出具体坐标，不为通过检查放开 GPL/LGPL 类别。

#### Scenario: 依赖含有待审许可

- **WHEN** 用户执行任一依赖许可检查入口，且运行时依赖中有未匹配白名单的项目
- **THEN** 两个入口均失败，报告列出真实待审依赖；此结果不改变源码许可头检查或依赖版本

### Requirement: 独立 JVM 依赖的轻量维护

项目 SHALL 依据上游 POM、官方许可和发行材料管理普通独立依赖，不维护其逐文件源码清单、源码头索引、审查哈希或固定二进制锁定。元数据政策 SHALL 按许可名称类别及别名匹配，不要求普通依赖逐版本人工审查；GPL/LGPL SHALL 不被通用类别规则放开。具体许可矛盾、修改或重新打包 SHALL 按实际情况单独处理。

#### Scenario: 普通独立依赖升级

- **WHEN** 独立依赖升级且没有具体许可矛盾或源码修改
- **THEN** 维护者依据上游许可、变更和发行材料检查，无需逐个源文件或类复核

#### Scenario: 日常 CI 与显式政策检查

- **WHEN** 日常 PR/push 运行许可材料 workflow
- **THEN** 运行材料验证，元数据政策仅在手动触发时独立执行；显式检查仍报告未匹配项，jump3r 已知疑问不因材料齐全而消除

### Requirement: 应用保留上游许可与必要补充

实际捆绑独立依赖的 Boot/Shadow 应用 SHALL 保留上游 JAR 自带的许可和声明。必要的补充许可与归属原文 SHALL 集中维护于单份 `licenses/jvm/open_source_licenses.txt`，随应用提供为 `META-INF/open_source_licenses.txt`；原始版权、许可和免责 SHALL 完整保留，必需文本缺失或损坏 SHALL 使材料检查失败。各应用 SHALL 共用此文件，各节仅适用于实际包含的相应组件，列出某组件 SHALL 不表示每个应用均使用它。普通库 SHALL 不附带本汇总。

#### Scenario: 构建包含已知缺少文本的依赖的应用

- **WHEN** 应用包含 Bouncy Castle、Protobuf、OnGres 或 RoaringBitmap 等清单中构件
- **THEN** 应用汇总保留相应的包级许可和归属原文、来源及适用范围；作者名单不呈现为本项目参与者，不核对依赖内部源码或固定二进制哈希

#### Scenario: 维护依赖升级后的许可材料

- **WHEN** 普通依赖升级
- **THEN** 保留上游自带声明，依据上游许可和发行材料更新汇总的适用段落，不维护逐版本补充映射或人工放行门禁，不要求逐文件审查

#### Scenario: 类库与应用的报告入口

- **WHEN** 用户构建普通类库或 Boot/Shadow 应用
- **THEN** 打包不依赖生成依赖报告；用户仍可通过显式命令按需生成报告及执行元数据政策检查

### Requirement: EPL 依赖的源码获取说明

系统 SHALL 在应用共用汇总中为实际捆绑的 Logback、Jakarta Annotation API 和 AspectJ Weaver 追加简短双语说明及实际版本的完整源码下载地址，明确 EPL-2.0 选择，并保留适用许可和原有声明。系统 SHALL 不为这些独立依赖下载、重复打入完整源码 JAR 或维护逐文件审查记录。普通库 SHALL 不被要求携带应用汇总或 EPL 源码材料。

#### Scenario: 构建包含 EPL 依赖的应用

- **WHEN** 构建实际包含这些 EPL 依赖的 Boot/Shadow 应用
- **THEN** 分发说明中的坐标与源码地址对应实际版本，许可全文和上游原声明保留；缺少对应地址或必要文本时核对失败

#### Scenario: 阅读 JVM 双语材料

- **WHEN** 用户查看仓库或应用中的 open_source_licenses.txt
- **THEN** 项目自写的范围、许可选择及源码获取说明具有中英对照，上游许可与归属原文不改写

### Requirement: 分发材料自动核对

项目 SHALL 提供可重复运行的归档和前端声明核对命令，并在 CI 执行代表性检查。核对 SHALL 覆盖项目双语声明、来源许可、ADPCM 对应源码、jump3r/EPL 依赖材料及 ZIP 路径唯一性，缺失或篡改材料 SHALL 导致失败。

#### Scenario: 产物丢失许可材料

- **WHEN** 指定的真实产物缺少应有声明或包含不匹配的源码与校验值
- **THEN** 核对命令失败并指出具体材料，不以普通构建成功代替材料验证

#### Scenario: Java 归档包含前端入口

- **WHEN** 普通、Boot 或 Shadow JAR 的 UI 资源目录中有 `index.html`，包括 Boot 嵌套的 Dashboard JAR
- **THEN** 核对命令要求同目录完整的 `THIRD-PARTY-FRONTEND-NOTICES.txt`，CI 验证至少一个实际包含该入口的 Boot JAR

#### Scenario: 归档中的前端许可与构建产物不一致

- **WHEN** 核对指定归档条目与对应前端构建生成的汇总，且条目缺失、截断或存在字节差异
- **THEN** 核对命令失败并指出归档和条目，CI 对代表性 Boot 和 Shadow JAR 执行此比较

#### Scenario: 本地和 CI 统一核对八个前端

- **WHEN** 用户或 GitHub Actions 执行共享前端核对脚本的默认流程
- **THEN** 八个前端按仓库内的锁文件安装并完成生产构建，实际汇总通过项目及适用前端许可检查，Dashboard 模板许可保留，docs 字体、原许可和双语说明在仓库、站点及汇总中一致；安装、构建、缺失材料或副本不一致返回非零状态并提供日志，本地跳过安装或仅核对旧产物的选项明确说明其限制

#### Scenario: 发布文档站点前核对材料

- **WHEN** 发布流程按仓库锁文件安装并构建文档站点
- **THEN** 两个部署目标共用经现有校验核对的同一站点目录，许可汇总、字体材料缺失或不一致时停止发布，站点不包含可编辑的 `xtream-codec.drawio`

#### Scenario: 使用统一材料检查入口

- **WHEN** 用户或 CI 执行 `build-script/license/check-materials.py`
- **THEN** 默认执行八前端完整流程，显式 `--jar`、`--frontend`、`--jar-frontend` 或 `--docs-dist` 时仅核对指定产物，快速前端选项不允许与指定产物混用；原有许可、字体、模板、源码、缺失与损坏检查保留，Python 测试通过单个明确的测试文件运行

### Requirement: 许可维护说明集中维护

项目 SHALL 将源码来源、音频比较、依赖政策、分发检查及 CI 用法集中在 `build-script/license/README.md`，删除被替代的说明并更新当前链接。固定来源、必要证据限制及具体待办 SHALL 保留，重复材料位置及验证过程 SHALL 精简；图片待核实范围 SHALL 保留在 `assets/STATIC-ASSETS.md`，路径与哈希清单 SHALL 按需生成。第三方许可材料的索引 SHALL 放在根目录的 `THIRD-PARTY-MATERIALS.md` 中，并从项目 README 链接到该索引。`licenses/` 中的分发材料及其路径 SHALL 保持不变，项目自写工具用法 SHALL 与实际命令一致。

#### Scenario: 查阅维护说明

- **THEN** 能找到统一检查命令及对应来源限制，未解决的 FFT、历史音频和图片事项保持明确，当前仓库文档无指向已删除说明的链接

# Design

## Context

当前动态编解码器已经分离不可变定义、编译布局和单次执行。新增能力沿用这三个层次，不把 JSON 配置解释带入运行时。Pair 没有 TLV 的条目长度头，按项数读取时必须继承外层边界。

## Goals / Non-Goals

实现 Pair 边界修复、编码字段生成、校验和核对、choice 默认分支和定义编辑支持。保持 schemaVersion 1 与现有 Java 构造签名兼容。不实现业务断言、复用类型、终止符、变长整数或任意前向表达式引用。

## Decisions

1. 字段增加可选 `generated`，包含互斥的 `constant`、`countOf`、`expression` 或 `checksum`。固定值与表达式用于线上标量；计数与校验和用于无符号整数。它们与 `computedLengthOf` 互斥。编码生成值优先于输入值，解码返回实际字段值，只有校验和执行核对。
2. `countOf` 指向同级集合，可指向后续字段；编码统计提供的集合元素数。表达式复用现有 AST 和显式启用的 XtreamExpressionEngine，只可引用先前可用字段。
3. `checksum` 使用 `algorithm` 和 `range`（同级单字段或 first..last）。首轮支持 xor8、sum8、crc32、crc32c；区间不得包含校验和字段，必须完整字节对齐。区间可以位于校验和之前或之后。复用现有区间起止事件，前置字段预留并回填，后置字段使用已计算结果；读取时以实际线上字节计算并比较。执行帧按需保存计算结果，重复元素互不影响。默认解码返回实际值及包含字段路径、算法、实际值、计算值的校验结果，不因校验不匹配中断解析；启用跟踪时附加警告。`DynamicDecodeOptions.STRICT` 是单次调用策略，不写入 Schema 或编译计划；严格模式校验失败抛出字段异常且不提交输入游标。结构错误和资源限制在两种模式下均保持失败语义。
4. `defaultVariant` 是 choice 的可选字段定义，未命中显式键时使用。默认分支遵守版本选择、作用域、条件和边界规则，与显式分支一起参与剩余边界分析。
5. Pair 的 item 边界传播与 array 一致。可能消费外层剩余空间的 counted Pair 不能出现在非末尾，也不能有多个条目共享边界；固定零条目允许后续字段，独立字节边界保持原语义。
6. 核心模块发布 Draft 2020-12 JSON Schema 资源和读取 API；调试页面使用相同资源提供属性、枚举与字段引用补全。采用现有文本编辑器和轻量补全模块，不增加大型编辑器依赖。结构约束由 JSON Schema 描述，跨字段依赖和版本关系仍由编译器检查。

## Risks / Trade-offs

- 字节区间的实际对齐依赖条件和运行时长度，因此无法静态证明的情况在执行时报告字段路径和 bit 偏移。
- 校验和覆盖的是实际线上字节，包括区间内长度前缀和填充；嵌套回填必须先完成再计算。禁止引用尚未回填的值，并校验区间事件依赖。
- 固定值不引入解码业务断言。报文首尾标志的强制检查由调用方完成。
- 增加 record 分量会改变规范构造器；保留旧签名重载以维持源码兼容。

## Validation

测试 Pair 编译拒绝与允许场景、旧 JSON/Java 入口、集合计数、表达式生成、已知校验和向量及损坏报文、前后置和嵌套回填、默认分支与边界。执行核心和调试器相关测试、UI 补全测试及构建、文档构建、样式检查和 OpenSpec 严格校验。

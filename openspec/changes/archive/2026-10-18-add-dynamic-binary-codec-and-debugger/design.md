# Design

## Context

见 `proposal.md` 的动机。当前 `EntityCodec` 以 Java 实体元数据为中心；`DataFieldEncoder` 能动态写入值，但其解码入口未实现，且 `DataField` 同时携带结构和值。`CodecTracker` 已提供可序列化的字段树和字节范围。现有 JT/T 808 页面具备成熟的 Trace 交互，但输入、接口和复制 HEX 的行为含协议假设。core 有按位读取及整数位段工具，尚无对称的通用位写入和位级 Trace 范围。

本变更须保持现有 `EntityCodec`、`DataField` 和协议实现的兼容性。动态引擎的设计依据是 `specs/dynamic-binary-codec/spec.md`；独立工具和跟踪扩展分别见对应规格。

## Goals / Non-Goals

**Goals:**

- 定义可经 JSON 交换、也可由 Java 构造的协议无关结构模型；在生产路径中编译一次、重复并发使用。
- 用统一的字段边界与游标语义支撑字节字段、连续位字段、嵌套容器及双向 Trace。
- 让独立调试应用与未来的 808 Starter 适配层使用同一业务入口和结果合同。

**Non-Goals:**

- 不将任意 Java 注解、`BeanPropertyMetadata` 或反射实例化能力直接暴露为 DSL 语法。
- 不重写 `EntityCodec`，不让现有生产编解码改走动态引擎，也不修改本次以外的 JT/T 808 页面。
- 不把 HTTP 或前端组件放进 `xtream-codec-core`；实体目录与可复用调试入口放入 core.debugger 包。

## Decisions

### 1. 动态引擎置于 core 的独立包

`io.github.hylexus.xtream.codec.core.dynamic` 下的 `schema` 子包提供结构模型与 JSON 转换，`engine` 子包提供编译器、不可变计划和执行上下文，`spi` 子包提供扩展接口及注册表。对外概念入口为 `compile(schema, registry) -> plan`、`plan.encode(values, ByteBuf)` 和 `plan.decode(ByteBuf)`，各自有可选 tracker 重载。计划保存已解析的字段引用与处理器，不保存请求值或游标。编译时完成结构和扩展解析，执行期不再通过字符串查找 Java 类。

模型构造时检查不依赖其他字段的规则，包括字段类型和局部属性组合、长度来源、固定选项范围、条件与表达式运算符及参数数量。字段顺序、前向引用、协议版本覆盖、剩余长度位置和扩展注册表仍在计划编译时检查。有限取值在 Java API 中使用枚举，JSON 保留原有字符串值；参数化的 `uN`/`iN` 仍使用类型名称。

替代方案是扩展 `DataField` 或复用 `EntityCodec` 的元数据类型。前者的值与定义耦合，后者依赖 Java 属性模型；两者都难以明确表示未知输入的长度边界和连续 bit 游标，因此不采用。基础编码原语、长度读写和 `CodecTracker` 可内部复用。

### 2. 单一规范结构模型，值按字段标识传递

结构以有序节点树表示。每个节点具有稳定 `id`、显示名称、节点类型和该类型适用的属性。节点 `id` 在所属结构中唯一，显示名称可以重复；值树按 `id` 或集合位置对应，避免重名字段覆盖。JSON 是结构模型的交换格式，不定义额外的文本解析语言；Java 调用方可通过构造器或 builder 构造同一模型。首版序列化格式包含 `schemaVersion`，以便将来升级。

概念示例：

```json
{
  "schemaVersion": 1,
  "fields": [
    { "id": "version", "type": "u3" },
    { "id": "flags", "type": "u5" },
    { "id": "length", "type": "u16", "endian": "big", "computedLengthOf": "payload" },
    { "id": "payload", "type": "bytes", "length": { "ref": "length", "unit": "byte" } }
  ]
}
```

整数采用 `uN` / `iN`（N 为 1–64），名称直接声明位宽，与 `Preset.RustStyle` 的常用整数命名一致。整数不再声明 `bits`，任意宽度仍可写成 `u3`、`u5` 等；浮点数和原始位串继续通过 `bits` 指定位宽。编译阶段把整数名称解析为计划中的执行类型和位宽，同时保留原始字段定义；执行阶段不重复解析，也不复制改写 DSL 字段。`ref` 指向已可用的字段标识，作用域规则在编译时确定。

外部协议版本通过 `compile(schema, version, registry)` 传入。字段的 `versions` 省略时为默认定义，显式整数数组表示适用版本；同一 id 的精确版本优先，缺少精确匹配时默认定义兜底，均无匹配则忽略。字段顺序由 id 首次出现的位置决定，重复或重叠的版本定义拒绝编译。嵌套结构、集合元素和分支递归沿用目标版本；筛选后完成引用和边界校验。生成计划保存固定的版本布局，调用方持有并反复执行，core 不引入全局缓存。已有默认 compile 重载只选择默认定义，ALL_VERSION 与 XtreamField 的默认匹配语义一致；schemaVersion 仍只描述 DSL 格式。

替代方案是从嵌套 UI 表单直接生成 `DataField[]`。它无法在无值时稳定解码，也无法承担跨客户端的持久结构合同。

### 3. 将 core 能力映射为内置节点与注册扩展

| core 能力 | 动态模型 |
| --- | --- |
| 有符号/无符号整数、大小端、浮点数 | 标量节点的位宽、符号和字节序 |
| 字符串、BCD、HEX、字节数组、填充 | 字节字段及字符集、长度、填充属性 |
| 固定/前置/引用长度、迭代次数、`@EncodedLength` | 带单位的边界规则、计数规则、区间长度节点 |
| 嵌套、List、Map、TLV、Pair | 结构、重复项、带判别键的有序条目 |
| 条件、版本、运行时类型 | 受控条件、版本选择与判别值分支 |
| `@DerivedField`、位标志 | 不消费输入的派生节点和位段视图 |
| 自定义 `FieldCodec`、转换器、日期时间等专用格式 | 已注册的双向扩展或内置专用节点 |

“覆盖”指这些可观察的编解码语义均有对应表达方式；不意味着序列化 Java 注解对象、任意 `FieldCodec` 类名或其容器反射上下文。对于日期时间等明确且通用的格式，优先提供内置节点；依赖业务类的处理逻辑经注册扩展接入。注册扩展约定编码、解码、配置校验及可选 Trace 元数据，调试应用只列出后端允许的扩展。

替代方案是允许 DSL 直接引用类名、SpEL 或任意脚本。这会把任意代码执行与实现细节带进持久定义，且难以迁移到其他应用，故不采用。内置条件采用有限的字段引用、常量、比较、布尔、算术和位掩码运算；复杂逻辑用注册扩展。

### 4. 边界规则先于读取，长度单位显式化

固定长度、前置长度、先前字段引用、容器剩余长度及集合计数各是独立规则，单位为 `bit`、`byte` 或 `item`。编译器检查引用顺序、唯一性、类型和依赖环；未受限的“剩余长度”只能在明确容器边界内作为终止节点。编码时按所选规则校验输入值和计算长度；自动回填长度可以通过占位写入和确定范围后的回填实现，解码时它只提供数值，引用它的字段仍需显式声明边界。这样保持 `@EncodedLength` 的现有语义。

TLV/Map/Pair 均以有序条目为执行基础。匹配键决定值结构，未知键按长度读取原始值；重复键保留为多条条目。Map 视图只在调用方明确选择且无覆盖歧义时生成。集合根据计数或字节边界停止，空进度循环属于执行错误。

替代方案是尝试从后续字段倒推出变长字段长度。遇到条件、嵌套或未知 TLV 时会有多解，不采用。

### 5. 统一 bit 游标与 Trace 范围

动态执行上下文以相对输入或输出起点的 bit 偏移作为唯一位置。字段顺序、引用值、容器边界和 Trace 由单次执行的公共状态管理，实际编码和解码分别进入独立执行类；长度回填只属于编码，缓冲区读取位置只在解码成功后提交。整字节字段要求已对齐；未对齐时必须有显式 `align` 规则。默认连续位顺序为 `msb0`，可在位容器中显式选择 `lsb0`；数值位序与字节序分别定义。位宽大于 64 的字段可作为 bit 字符串或字节序列处理，不隐式塞入 `long`。编码尾部填充和解码时填充校验使用同一规则。

Trace 节点新增可选 `[bitStart, bitEnd)`。现有 `[byteStart, byteEnd)` 保留，动态位节点对应的字节范围按触及的字节向外取整。位段视图引用源整数的 bit 区间，不推进游标；连续位节点推进游标。字节索引仍可将同一字节映射到多个位节点，页面再按 bit 范围细分高亮。现有实体 Trace 未提供 bit 字段时保持原行为。

替代方案是只记录所在字节。对于共享字节或跨字节位段无法准确定位，不满足调试需求。

### 6. 独立工具分成可复用服务与运行入口

在 core 的 `io.github.hylexus.xtream.codec.core.debugger` 包提供可复用调试入口、实体目录和请求/响应，不单独发布服务模块。请求值、响应值和实体模板使用 `Map<String, Object>`，嵌套对象和数组使用 Map/List；动态模式直接传给 DynamicValues，实体模式经宿主提供的 DebugEntityValueMapper 转换为注册实体。该接口仅定义 Map 转实体、实体转 Map，不暴露 Jackson 类型。默认使用 Jackson2DebugEntityValueMapper，宿主可向该适配器传入已配置的 ObjectMapper，或实现自己的转换器。Java 调用方无需构造 JsonNode，HTTP 仍以同样的 JSON 对象交换。core 以 api 保留 jackson-annotations，以 compileOnly 编译 jackson-databind，移除生产 spring-boot-starter-json；宿主使用 Jackson 2 专用入口时显式提供 databind，独立 HTTP 应用直接声明该依赖。

DynamicSchemaJson 将 mapper 和 Jackson 异常处理放入延迟加载的内部类，只有 JSON 读写才初始化。Java 动态计划、普通实体编解码、自定义实体值转换器和 JSON Schema 资源读取不需要 Jackson 2 实现。单独的 testWithoutJackson 任务只使用 core 生产依赖和 JUnit，验证上述路径与 Jackson 实现缺失，并纳入 check；同时检查 core 运行时依赖与发布元数据不再传递 databind 或 JSON starter。普通实体编解码的 SpEL 需要 spring-context，core 显式声明该实现依赖，避免依赖 JSON starter 间接提供它。

服务仅保留目录参数的默认构造器，以及目录、值转换器、DynamicCompileOptions、DynamicLimits 的完整构造器；扩展注册表统一来自编译配置。转换器负责实体模板、编码输入和两个方向的响应值，动态模式不调用转换器。转换器必须支持服务并发调用，失败抛出运行时异常并沿用现有失败响应；模板转换失败直接报告给调用方。未来增加 Jackson 3 适配器时保持服务和转换接口签名，本次不增加 Jackson 3 依赖，也不改变 core 其他既有 Jackson API。

调试应用模块直接依赖 core，另有独立前端工程；core 的调试逻辑不依赖 HTTP 容器。实体由显式注册和受限包扫描组成，API 只接受目录标识。应用模块使用 JDK 21 的 `HttpServer` 提供小规模版本化 API 与静态资源，限制请求体大小和可访问资源；这是目前所需依赖和路由代码最少的选择。Netty HTTP 是可选替代，但当前没有流式上传或高并发连接要求，新增路由、资源及错误处理代码更多。

Java 请求的 mode 使用 `DebugCodecMode`（ENTITY/DYNAMIC），direction 使用 `DebugCodecDirection`（ENCODE/DECODE），服务按枚举处理并穷尽模式分支。JSON 继续使用 entity/dynamic、encode/decode；请求构造器拒绝缺失或 null，JSON 转换拒绝未知名称，HTTP 统一返回 400 请求错误。

808 Starter 将来可以直接调用 core 的调试入口，在既有 Spring MVC/WebFlux 路由上实现同样的 API 合同，无需启动独立应用或重做动态引擎。本次验证 core.debugger 不引用独立 HTTP 实现，不新增 808 路由。前端在独立项目中实现两种模式；现有 React Trace 交互可复制并清除 `7e` 等协议假设，或抽取协议无关组件，不引入 808 项目作为运行时依赖。

### 7. 错误、资源和性能边界

计划编译报告定义路径；执行异常报告字段路径、bit 偏移和原因。解码结果包含消费的 bit/byte 数及剩余输入，不能无声吞掉尾部。最大输入大小、最大输出大小、集合项数和嵌套深度由动态引擎限制；同步 Java 扩展不能由 core 安全强制中断，其处理时间由宿主调用超时控制。默认生产 API 提供合理上限并允许调用方显式覆盖。调用方传入的 `ByteBuf` 所有权保持在调用方；内部临时缓冲区由引擎释放。失败跟踪保留已经完成的节点及诊断。

未传 tracker 的执行走不创建节点的路径。计划可并发复用，但值树和单次执行上下文不共享可变状态。用同一结构验证 tracker 与非 tracker 路径字节和结果相等；用基准测试观察相对于现有实体编解码路径的开销，性能门槛以回归趋势而非未经测量的固定倍率表示。

### 8. React 可视化工作台

本轮将 debug/xtream-codec-debugger-ui 迁移为 React、HeroUI 3、Tailwind 4 和 Vite，由 pnpm 管理。工作台使用通用 /api/v1 调试合同，开发时通过 Vite 代理连接独立应用，生产产物继续随 Java 应用打包；不加入 1078 或 808 协议假设，暂不迁入 808 Dashboard。JT1078 调试前端保持原有实现。

前端打包统一使用仓库的 XtreamCodecFrontendBuildExtension，由根项目构建任务执行锁文件安装、前端测试和 Vite 构建，再通过 copyFrontendDist 复制到独立应用资源目录。构建开关默认开启以保证首次启动可用，关闭后沿用已生成资源。插件提供 additionalInputs，跟踪 Vite 与 TypeScript 配置、入口 HTML、workspace、测试和共享 JSON Schema，避免增量构建遗漏这些变化。复制前清理旧哈希产物，生成资源不提交到 Git。

页面提供深色与明亮主题，以颜色区分数值、文本、容器和生成字段。编辑器直接操作原有 DynamicSchema 与独立字段值，提供递归结构、数组、增删改复制和排序；完整 JSON 编辑及导入导出保留高级 DSL 属性。值按字段标识绑定，排序不改变字段值；大整数保持无损。实体和动态模式分别保存输入草稿，单字段试验使用独立动态定义。后端执行仍是唯一二进制编解码实现，页面不模拟结果。结果展示原始 HEX、精确 bit 范围、校验核对、剩余输入和部分失败 Trace。组件、API 合同及主题样式保持独立，便于验收后复制到 Dashboard。

## Risks / Trade-offs

- **DSL 覆盖范围过大导致模型堆积专用属性** → 先实现公共节点和边界规则，专用格式通过注册扩展接入；按能力映射表及规格场景验收，不复制注解属性全集。
- **位序、大小端和填充概念混淆** → 分开建模并提供混合位/字节、跨字节及不对齐的往返测试和示例。
- **长度回填与条件字段相互影响** → 对最终执行的字段区间计数，编译时校验引用；测试跳过字段、嵌套字段和回填边界。
- **用户结构或扩展造成资源耗尽** → 编译与执行均限制深度、元素数、缓冲区大小，HTTP 入口另限制请求体；扩展只能由宿主注册。
- **调试页面复制的 Trace 组件仍残留 JT/T 808 行为** → 明确检查复制 HEX、标题、示例数据和接口路径；用协议无关字节样例验证。
- **core 调试入口依赖独立 HTTP 实现会阻碍宿主复用** → 用独立应用仅依赖 core 的模块配置及服务级测试保证单向依赖。

## Migration Plan

1. 在 core 增加动态能力和位级 Trace 附加字段，保留现有入口；先以独立测试覆盖双向语义。
2. 增加可复用调试服务、独立轻量 HTTP 应用和前端，联调实体与自由组合模式。
3. 补全文档、示例及性能基准，验证 core、调试应用与前端构建。已有 `DataField` 与 `EntityCodec` 无迁移要求。
4. 将来需要在 808 Starter 中提供同样能力时，只增加该 Starter 的路由与页面入口；此步骤不属于本次实施。

回滚可移除新模块和 core 的动态包；位级 Trace 的可选字段可独立回退，不影响既有字节范围调用方。
